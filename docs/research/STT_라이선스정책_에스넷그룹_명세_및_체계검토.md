# On the Record — 라이선스 정책 수립 보고서 (대상 조직 명세 · 라이선스 체계 검토)

**문서 버전: V1.6.0** (2026-11-05) · 상태: MIT 정책·공개 승인·Obsidian 디렉터리 정책 반영 확인, artifact별 검토 미완료 · 변경 내역은 §11 문서 이력 참조

> **결론:** 프로젝트 자체 코드의 라이선스 정책은 MIT이며, 임직원 혜택은 라이선스를 제한하지 않는 **§9의 추가 지원**(반입 심의 패키지·사내 프리셋·검증된 하드웨어 프로파일·우선 지원·교육)으로 제공한다. 저작권자 `에스넷시스템`과 공개 승인은 2026-11-05 사용자 확인을 받았다. Obsidian 디렉터리 정책을 검토해 사용자 관리 런타임·모델 방식을 반영했다. 실제 배포 구성요소별 권리·의무 검토가 남아 있으므로 완료 전까지 공개 릴리스는 보류한다.

- 블루로터스㈜는 에스넷시스템의 **최대주주(지주사 역할)** 이며, 대표이사 허인숙(45.3%)·박효대(42.9%)가 주요 출자자다. 에스넷시스템의 계열회사 명세에는 포함되지 않는다(상위 회사).
- 에스넷시스템 지분: 블루로터스 14.76%, 박효대 5.35%, 허인숙 5.90%, 특수관계인 합계 26.01%.
- ㈜인성정보는 에스넷시스템이 **경영참여 목적으로 19.09%를 보유한 상장 관계사**이며, DART 계열회사 명세에서는 제외되고 타법인출자(경영참여)로 분류된다.

### 2.7 DART 명세의 한계

- 기준일이 **2025-12-31**이라 2026년 중 지분·계열 변동(하이케어넷 관계기업 전환, 인성정보 지분 확대)이 반영되지 않았다.
- 비상장 계열사(굿어스 계열, 해외 법인)는 개별 공시가 없어 DART로는 모회사 사업보고서에 기재된 범위까지만 확인된다.
- 블루로터스㈜는 비상장으로 자체 사업보고서가 없어, 명세는 에스넷시스템 사업보고서의 최대주주 항목에 의존한다.
- 사업보고서 계열회사 명세는 **공정거래법상 기업집단 지정과 다른 개념**이다. "그룹"의 법적 정의가 필요하면 공정거래위원회 기업집단포털을 별도 확인해야 한다.

| R4 | 옵시디언 **오픈소스 커뮤니티** 대상 공개 배포 | 외부 사용자를 배제할 수 없음 |
| ~~R5~~ | ~~대상 외 사용자는 "무료 제공"이 아님을 표현하고 싶음~~ | **기각(2026-11-01)** — MIT 확정으로 성립하지 않는다. §3.4 참조 |

> **R5 기각 근거 (V1.0.1 추가):** R5는 "임직원은 무료, 그 외는 무료가 아님"을 전제했으나, MIT는 대상 구분 없이 전원에게 무료 사용을 허용한다(§4.5-1). 따라서 R5는 애초에 충족할 수 있는 요구가 아니며, 차별화 요구는 §9 사내 혜택으로 흡수한다.

### 3.2 요구사항 간 충돌 지점

- **R1·R2 vs R4 (V1.0.1 정정):** 재직 기간·기기 한정은 **라이선스로 표현할 수 없다.** MIT는 대상을 구분하지 않으므로, 커뮤니티 등록 후에는 일반 사용자도 같은 코드를 설치한다. R1·R2는 **§9 혜택의 적용 범위**로만 표현한다.
- **R5 vs R4:** Obsidian 커뮤니티 디렉터리 FAQ는 **Free / Optional payment / Paid** 세 가지를 구분하고, "결제 없이는 쓸 수 없으면 Paid", "일부 기능을 결제 뒤에 두면 Optional payment"로 규정한다. 즉 *차별화*는 허용되지만, 디렉터리 등록을 유지하려면 등록 라벨과 README 공개 내용이 일치해야 한다.
- **결론 (V1.0.1 갱신, 정책 선택):** R1~R3은 **라이선스가 아니라 §6 정책 문서와 §9 사내 혜택**으로 다루고, **R5는 기각**한다. MIT 선택은 라이선스 정책 결정이며 권리 귀속·공개 승인 또는 Obsidian의 별도 플랫폼 정책 검토를 대신하지 않는다.

### 3.3 라이선스로 표현할 때의 대안

| 표현 방식 | 가능 여부 | 문제 |
|---|---|---|
| MIT + 사내 정책 문서 | **채택 (§5 A안 확정)** | 라이선스로는 "우대"가 없음 → §9 혜택으로 보완 |
| 비상업 라이선스(PolyForm Noncommercial) | 기술적으로 가능 | 회사 내부 **업무** 사용이 상업 목적일 수 있어 임직원 사용이 오히려 위험 |
| FSL/BUSL (일정 기간 후 오픈소스 전환) | 기술적으로 가능 | 공개 배포 시 커뮤니티 반감, 디렉터리 'Custom license' 경고 |
| "지정 회사만 무료" 맞춤 라이선스 | 사실상 불가 | OSI 미승인 → 오픈소스 아님. 디렉터리 스캐너가 Custom license로 경고 |
| 회사 전용 비공개 배포 + 커뮤니티는 별도 | 기술적으로 가능 | 코드 이중 관리·옵시디언 생태계 기대와 충돌. **본 정책에서 채택하지 않음(§9.1-4: 등재본 변형 금지)** |

## 4. 라이선스 체계 리뷰

### 4.1 분류 틀

| 층 | 정의 | 해당 라이선스 |
|---|---|---|
| 오픈소스 (OSI 승인) | 사용·수정·재배포·상업적 사용 자유 | MIT, Apache-2.0, BSD-3-Clause, MPL-2.0, GPL-3.0, AGPL-3.0, LGPL |
| 소스 공개형 (source-available) | 코드는 보이지만 용도 제한 | BUSL-1.1, Elastic License 2.0, SSPL, FSL-1.1, PolyForm 계열 |
| 비상업 전용 | 비영리·개인 목적만 | PolyForm Noncommercial 1.0.0, CC BY-NC 4.0, Prosperity |
| 독점 | 비공개·상용 계약 | 사내 EULA, 상용 라이선스 |

- OSI 승인 목록(https://opensource.org/licenses)에서 **SSPL·Elastic License·Business Source·PolyForm·Functional Source는 조회되지 않는다**. MIT·Apache-2.0은 조회된다(2026-11-01 확인).
- SPDX 라이선스 목록에는 `FSL-1.1-MIT`, `FSL-1.1-ALv2`, `BUSL-1.1`, `Elastic-2.0`, `PolyForm-Noncommercial-1.0.0`, `PolyForm-Small-Business-1.0.0`, `SSPL-1.0`이 모두 등록되어 있어, **식별자는 표준이지만 OSI 승인 오픈소스는 아니다**는 구분이 핵심이다.

### 4.3 "지정 회사 무료"를 표현하는 표준 장치

| 장치 | 무엇을 하는가 | 이 프로젝트 적용 |
|---|---|---|
| GPL §7 Additional Permissions | GPL 조건에서 **예외를 허용**(완화)하는 조항. 제한을 추가하는 장치는 아니다 | 해당 없음(GPL 사용 안 함). "추가 권한은 완화만 가능"이라는 원칙은 기억할 가치가 있음 |
| MIT + 별도 정책 문서 | 라이선스는 전원에게 동일, 우대는 계약·정책으로 표현 | **채택(확정)** |
| 추가 약관(Additional Terms) 파일 | Apache-2.0 제5조 등에서 허용되는 범위 내 별도 조건 | 불필요 — MIT에는 추가 조건 부과 구조가 없음 |
| 상표 라이선스 분리 | 코드는 열고 이름·로고는 통제 | 부분 적용(제품명·로고 통제, 코드는 MIT) |
| Dual licensing | 오픈소스 + 상용 라이선스 병행 | C안(EE 모듈)으로 보류 |
| CLA / DCO | 외부 기여자의 권리 정리 | DCO 권장(기여 유도), CLA는 과함 |
| 사내 사용 정책(User Policy) | 재직 중 혜택·지원 범위·퇴사 후 조건 명시 | **채택(확정)** |

- 업계 선례는 "내부 사용은 자유, **서비스로 재판매**만 제한"이다. Elastic License 2.0은 관리형 서비스 제공·라이선스 키 우회를 금지하고, n8n의 Sustainable Use License는 내부 업무 사용을 허용하면서 재판매를 제한한다. 즉 **"구성원 무료"는 라이선스가 아니라 내부 사용 조항으로 해결하는 것이 일반적**이다.

### 4.5 결론 — 새 라이선스를 만들 필요가 있는가

**없다.** 이유는 세 가지다.

1. **요구사항을 라이선스가 담을 수 없다.** MIT는 이미 모든 사용자(임직원 포함)에게 무료 사용·수정·상업적 사용을 허용한다. 임직원에게 주려는 것은 "허가"가 아니라 "무료 지원·사내 배포·교육"이라는 **추가 약속**이며, 이는 라이선스 밖의 문서로 표현해야 한다.
2. **제한형 라이선스는 요구를 오히려 배반한다.** 비상업(PolyForm Noncommercial)으로 가면 회사 내부 *업무* 사용이 상업 목적으로 해석될 수 있어, 정작 정부·비영리·학교 대상 목표(R4)와 임직원 사용(R1·R2)이 동시에 위험해진다.
3. **비용 대비 편익이 나쁘다.** 맞춤 라이선스는 OSI 승인을 받을 수 없어 디렉터리 경고·커뮤니티 신뢰 손실을 부르고, 얻는 것은 "다른 회사도 무료로 쓸 수 있다"는 사실의 차단뿐인데, 이는 애초에 코드 공개로 포기한 권리다.

### 4.6 윤리 검증 — 소속에 따라 허용·제한하는 것이 옳은가

제기된 문제의식: "누군가에게 허용하고 누군가에게 제한하는 라이선스를 만드는 것이 옳은가, 옵시디언 플랫폼에서 상도에 맞는가."

| 검증 축 | 확인 내용 | 판정 |
|---|---|---|
| 오픈소스의 정의 | Open Source Definition 제5조 "No Discrimination Against Persons or Groups"(어떤 사람·집단도 차별하지 말 것), 제6조 "No Discrimination Against Fields of Endeavor"(활동 분야를 차별하지 말 것), 제7조 "권리는 재배포받는 모든 이에게 추가 라이선스 없이 적용" | **특정 회사를 지목해 허용/제한하는 라이선스는 정의상 오픈소스가 될 수 없다** |
| 업계 제한형 관행 | Elastic License 2.0은 관리형 서비스 제공·라이선스 키 우회를, FSL은 경쟁 제품 사용을, n8n Sustainable Use License는 재판매를 제한 | 제한의 기준은 **사람이 아니라 행위**다 |
| 회사 기준의 유일한 예외 | PolyForm Small Business 1.0.0 — 직원·계약자 100명 미만 **그리고** 전년 매출 100만 USD 미만 | 지목이 아니라 **객관적 수치 기준**이라 명단형 특혜가 아니다 |
| 플랫폼 집행 가능성 | 옵시디언 디렉터리 라벨은 Free / Optional payment / Paid 세 가지이고 설치·배포는 사용자 신원을 확인하지 않는다 | **신원 기반 제한을 집행할 기술적 장치가 없다** |
| 상도의 관점 | 차별은 타인에게서 권리를 **박탈**할 때 발생한다. MIT는 이미 전원에게 무료 사용을 허용하므로, 임직원에게 지원·교육을 **추가로 주는 것**은 아무의 권리도 줄이지 않는다 | 차별이 아니다. 문제가 되는 것은 제한 그 자체가 아니라 **제한의 근거를 행위가 아닌 사람·소속에 두는 것** |

**검증 결론:** "에스넷그룹만 무료" 같은 명단 지목형 라이선스는 ①오픈소스 정의 위반 ②업계 관행 부재 ③플랫폼 집행 불가의 삼중 문제를 안는다. 반대로 MIT + 임직원 지원 우대 구조는 **윤리적으로도, 실행 가능성에서도** 요구사항을 충족한다. 즉 애초에 "누군가를 제한하는 라이선스"를 만들 필요가 발생하지 않는 설계다.

### 0-ENV-10 의존 구성요소 라이선스 검토 결과 (2026-11-01)

**결론:** 확인한 upstream 라이선스에서 MIT 플러그인 코드와의 일괄적인 충돌은 발견하지 못했다. 다만 런타임·모델·오디오 변환기의 실제 배포 파일과 버전은 아직 선정되지 않았으므로, 아래 조건을 충족하기 전에는 최종 SBOM이나 반입 심의용 라이선스 명세로 간주하지 않는다.

| 구성요소 | 확인한 라이선스·근거 | MIT 공개 및 배포 판단 |
|---|---|---|
| 현재 플러그인 런타임 | `package.json`에는 `dependencies`가 없고 빌드·개발 도구만 `devDependencies`로 선언되어 있다. 소스에는 녹음 파일 감지와 안정화 로직이 있으나 STT 엔진·모델·오디오 변환기를 제품 코드에 통합하지 않았다. | 현재 제품 코드에 포함되지 않은 whisper.cpp, 모델, 오디오 변환기 및 추가 분석 기능은 실제 선택·배포 시 artifact별로 검토한다. 현재 개발 의존성과 추후 설치할 런타임을 혼합해 SBOM을 작성하지 않는다. |
| `whisper.cpp` 및 `ggml` 코드 | 공식 upstream 저장소의 각 `LICENSE`는 MIT이다. whisper.cpp upstream README는 기본 CLI가 16-bit WAV만 입력으로 받으며 별도 변환 예로 FFmpeg를 안내한다. | MIT 공개와 양립 가능하다. 바이너리를 재배포하면 해당 코드의 저작권·라이선스 고지를 보존한다. 공식 릴리스 또는 자체 빌드의 선택적 backend와 포함 DLL은 별도 구성요소로 확인한다. |

## 9. 사내 혜택 정책 (에스넷그룹 임직원 전용)

### 9.1 설계 원칙

1. **MIT가 주는 것을 혜택으로 세지 않는다.** 사용·수정·배포 권한은 이미 전원에게 있다. 혜택은 **MIT가 줄 수 없는 것**에서만 만든다: 사내 맥락 정보(용어·조직·기기), 심의 문서, 지원, 교육.
2. **코드에 비공개 기능을 두지 않는다.** C안(별도 상용 모듈)은 보류했으므로, 모든 혜택은 **코드 밖의 자산**(문서·설정 파일·사람)으로 구성한다. 사내 전용 코드 분기를 만들지 않는다.
3. **중단 가능해야 하지만, 사후 회수는 요구하지 않는다.** 재직 종료 시 *혜택의 제공*(지원·사내 배포·자료 접근)만 끊고(§6.3), MIT가 부여한 사용 권한과 이미 제공된 코드·자료는 회수하지 않는다. 조기 접근 빌드도 같은 원칙을 따른다.
4. **등재본을 변형하지 않는다.** 사내 배포·설정은 공식 플러그인과 **같은 코드**를 사용한다. 사내용 별도 빌드는 만들지 않는다.

### 9.2 혜택 목록

|---|---|---|---|---|

### 9.3 규정 근거와 제약

| 항목 | 내용 |
|---|---|
| 규정 근거 | Obsidian 정책은 **공식 디렉터리 등재 플러그인에만 적용**되며, 디렉터리 밖에서 설치하는 플러그인에는 적용되지 않는다(§4.4 인용). 따라서 사내 배포·사내 프리셋 운영은 공개 조건과 독립적이다 |
| 제약 1 | 등재 플러그인은 **스스로 또는 의존성을 설치·업데이트할 수 없다.** 프로젝트는 런타임·모델에도 보수적으로 적용해 플러그인이 다운로드·설치·업데이트·삭제하지 않도록 한다. 사용자가 플러그인 외부에서 직접 관리하고, 플러그인은 경로·파일 검증과 실행만 한다 |
| 제약 2 | 혜택은 MIT 조건을 **변경하지 않는다**. 사내 프리셋·문서는 별도 저작물이며, 플러그인 코드의 라이선스는 MIT로 유지된다 |
| 제약 3 | 반입 심의 패키지에 포함하는 SBOM·라이선스 명세는 `0-ENV-10`(의존 구성요소 라이선스 확인) 완료 후 확정한다 |
| 제약 4 | 사내 프리셋에 회의 녹음·전사 결과 등 개인정보가 포함되지 않도록, 용어집은 회사명·제품명·약어만 담는다 |
