## 1. 요약 및 권고안

Obsidian 코어 **Audio recorder**를 그대로 사용하고, 플러그인은 녹음 파일이 만들어지는 흐름을 감시해 녹음이 끝난 뒤 전사를 자동 시작하는 방식을 제안한다. 사용자가 플러그인의 파일 찾기 버튼으로 기존 오디오를 선택하는 경우에도 선택 직후 자동으로 전사를 시작한다. 플러그인은 녹음이나 코어 플러그인을 대체하지 않으며, 설정·자동 감지·전사·검토·노트 반영을 담당한다.

이 계획서에서 **상황특화**란 녹음 오디오에서 발화 내용을 전사하고, 회의에서 지정한 단어·표현 및 사람 이름·지역명·회사명·제품명 등 고유명사의 언급 위치를 찾아 회의 맥락 검토를 돕는 방향을 말한다. 장기적으로 화자 분리와 주변 환경음·공간 단서 분석도 검토할 수 있지만, 이 기능들은 기본 Whisper/`whisper.cpp` CPU 전사의 기능으로 간주하지 않는다.

이번 첫 구현은 `whisper.cpp`가 제공하는 전사와 구간 단위 timestamp를 검증한 범위까지만 약속한다. 구간 안의 특정 단어가 언급된 위치는 해당 발화 구간 timestamp로 안내하며, 단어 시작·끝 시각이 필요한 정밀 위치는 별도 정렬 모델/provider를 조사·검증하기 전까지 제공한다고 표기하지 않는다. 고유명사 후보의 발생 위치도 첫 단계에서는 이를 포함한 전사 구간을 가리키는 수준으로 제한한다. 화자 분리, 단어 수준 정렬, 고유명사 자동 추출, 환경음/공간·상황 분석은 각각 별도 모델 또는 처리 단계의 타당성·정확도·성능을 입증한 후 추가한다. 모든 분석 결과는 관찰값, 모델 추정 및 미검증 기능을 구분하고 사용자가 확인할 수 있게 한다.

대부분의 지속 설정(기본 모델, 언어, 장치, 자동 감지, 결과 삽입 방식 등)은 Obsidian 플러그인 설정 화면에서 관리한다. 회의 중에는 코어 녹음 시작/종료 또는 플러그인의 파일 선택처럼 최소한의 입력만으로 작업이 시작되도록 한다. 자동 트리거는 전사 작업 시작을 뜻하며, 노트에 결과를 반영하는 것은 기본적으로 사용자의 검토·승인 후에 수행한다.

핵심 설계 결정은 다음과 같다.

1. **CPU 전사를 항상 사용 가능한 기준 경로**로 둔다. 현재 지원 대상인 Windows x64용 `whisper.cpp` CPU 실행 파일과 양자화 Whisper 모델을 먼저 검증한다. OS와 CPU 아키텍처별 배포물 추가는 provider 경계와 manifest를 통해 확장할 수 있게 설계한다.
2. **가속기는 선택 가능한 provider**로 취급한다. NVIDIA GeForce GTX 계열은 검증된 CUDA 경로, Intel Iris Xe 및 UHD Graphics는 검증된 Intel GPU 경로를 각각 시험한다. 하드웨어 이름만 보고 가속 성공을 가정하지 않는다.
3. **운영체제·CPU 아키텍처·실행 provider·모델을 독립적으로 선택**한다. 이번 지원 범위는 Windows 데스크톱이며, macOS/Linux는 제외한다. Windows의 OS/아키텍처별 실행 파일 및 가속기 지원은 manifest로 등록하고 새 조합은 provider 추가와 검증으로 확장할 수 있게 한다.
4. 런타임·모델은 사용자가 직접 별도 취득·설치하고 vault 밖의 사용자별 로컬 위치에 둔다. Obsidian 커뮤니티 디렉터리 정책을 보수적으로 적용해 플러그인 안에서 다운로드·설치·업데이트·삭제하지 않는다. 설정 화면은 사용자가 지정한 파일의 탐지·경로·버전·해시 확인과 시험 실행만 제공한다.
5. 우선 `whisper.cpp` 기반 CPU 전사와 구간 timestamp를 구현·검증한다. 전사문 내 검색은 일치 항목이 포함된 구간 timestamp를 제공한다. 단어 timestamp, 자동 고유명사 추출, 화자 분리 및 환경음/공간 분석은 코어 기능으로 가정하지 않고 별도 기술 검증을 통과한 뒤 확장한다.
6. 프로젝트 자체 코드에는 MIT를 적용한다. 본 프로젝트는 박성원 개인의 오픈소스 프로젝트이며 저작권자는 `SUNGWON PARK (박성원)`이다. 플러그인은 외부 바이너리나 모델을 번들링 배포하지 않으며 사용자 로컬 관리 방식을 따른다.

## 2. 문제와 사용자 흐름

사용자는 회의 중 Obsidian 코어 녹음 기능으로 음성을 기록한다. 현재 녹음 파일을 회의록에 활용하려면 별도 전사 도구, 환경별 런타임 구성, 결과 복사 작업이 필요하다. CPU만 있는 노트북부터 Intel 내장 GPU와 NVIDIA GPU가 있는 데스크톱까지 성능과 설치 조건이 달라 하나의 실행 방식에 의존하면 지원 환경이 제한된다.

### 목표 사용자 경험

1. 사용자는 대부분의 기본값과 자동화 정책(모델, 언어, 실행 장치, 녹음 감지, 결과 반영 방식)을 Obsidian 플러그인 설정 화면에서 미리 지정한다.
2. 사용자가 Obsidian 코어 Audio recorder로 녹음을 시작하면 플러그인은 공개 API로 관찰 가능한 파일/노트 변경을 통해 산출물을 추적한다. 코어 recorder 시작 이벤트 자체에 직접 연결된다고 가정하지 않으며, 녹음 중인 파일은 전사하지 않는다.
3. 사용자가 코어 녹음을 종료하고 파일이 저장·안정화되면 플러그인이 별도 전사 명령 없이 전사 작업을 자동으로 대기열에 넣고 시작한다. 기존 오디오를 찾을 때는 플러그인의 **파일 찾기** 버튼에서 선택하는 즉시 전사를 시작한다.
4. 플러그인은 로컬 런타임으로 전사하고 진행률·취소를 알린다. 검색 결과는 검증된 segment timestamp에 연결한다.
5. 사용자는 전사 원문과 구간 시각을 검토·편집하고 승인한다. 승인된 결과만 지정 위치에 삽입하며 기존 내용은 묵시적으로 덮어쓰지 않는다.
6. 파일을 감지할 수 없거나 여러 파일이 모호한 경우 파일 선택 버튼을 제공한다. 런타임 누락, 파일 불안정, 전사 실패 시에는 자동 실행을 멈추고 설정/오류 안내를 표시한다.

Obsidian 코어 Audio recorder는 녹음 파일을 vault에 저장하고 활성 노트에 오디오 링크를 삽입한다. 공개 API가 녹음 시작/종료 이벤트 자체를 제공한다고 가정하지 않는다. 첫 설계는 vault 파일·노트 변경 이벤트와 파일 크기/수정 시각의 안정화, 공개 MetadataCache를 통한 링크 확인으로 녹음 진행 및 종료를 추론한다. 2026-11-05 한 차례의 실제 시험에서는 파일 생성 후 약 2초 뒤 노트가 수정되고 최종 embed가 확인됐으나, 수정 시각은 링크 삽입 시각의 대리값이며 반복 검증이 필요하다([시험 기록](../baselines/OBS-03_AUDIO_NOTE_LINK_TIMING_2026-11-05.md)). 안정화 뒤에도 링크가 확인되지 않으면 제한 시간 후 자동 처리를 중단하고 안내·파일 찾기 경로를 제공한다. private API나 내부 이벤트는 사용하지 않는다.

## 3. 범위와 제외 범위

### 이번 설계 범위

- Obsidian 데스크톱 커뮤니티 플러그인의 로컬 오디오 전사
- Obsidian 플러그인 설정 화면을 통한 지속 설정과 코어 Audio recorder 완료/플러그인 파일 선택에 따른 자동 전사 시작
- CPU 기본 동작 및 선택형 NVIDIA GTX / Intel Iris Xe·UHD Graphics 가속 경로
- Windows 데스크톱 전용 지원과 CPU 아키텍처별 런타임 확장이 가능한 구조
- 설정 화면에서 런타임·모델, 기본 전사 옵션, 자동 감지·트리거 정책 관리
- 노트 내 녹음 탐색, 전사, 결과 미리보기·편집, 노트 삽입
- CPU 기준 단계에서는 전사 segment timestamp 및 전사문 내 검색어가 포함된 segment의 시각 제공
- 별도 검증 후 word alignment, 고유명사 후보 추출, 화자 분리, 환경음 분석을 연결할 수 있는 확장 경계
- 환경 감지, CPU fallback, 오류·취소·개인정보 보호
- 업무·상황별 용어와 후처리 형식을 확장할 수 있는 프로필 경계

### 이번 범위에서 제외

- 오디오 녹음 기능 자체의 구현 또는 코어 Audio recorder 대체
- 전사 완료 직후 자동으로 노트를 덮어쓰는 동작
- 클라우드 전사·외부 API 업로드
- 이번 두 PC를 넘어선 가속기 전체의 성능 보장
- **모바일 버전 전체:** Obsidian 모바일 앱에서의 플러그인 설치·실행·설정·사용자 관리 런타임 연결·전사를 지원하지 않는다.
- **macOS 및 Linux:** 이번 개발계획과 릴리스의 대상이 아니다. 별도 후속 범위로 다룬다.
- 음성만으로 화자의 실제 신원·실명 또는 고유명사 대상과 화자의 연결을 확정하는 기능
- 주변 음향만으로 특정 장소·상황의 사실을 확정하거나 녹음에 없는 맥락을 만들어내는 기능
- `whisper.cpp` CPU 전사만으로 화자 분리, 단어별 정밀 timestamp, 고유명사 자동 추출, 음향 장면 분류가 제공된다고 가정하는 것
- 사실 검증 없이 STT 결과를 요약문·결정사항으로 자동 확정하는 기능

본 플러그인은 Desktop Only로 개발한다. 모바일 호환 UI나 모바일용 추론 경로는 이번 범위에 포함하지 않으며, 모바일 지원은 별도의 향후 제품 범위로 다시 결정하기 전까지 제공하지 않는다.

## 4. 조사한 시스템과 환경별 제안

개발자는 물리적으로 떨어진 PC·노트북을 최소 2대 이상 사용하며, 아래 두 시스템이 현재 확인된 기준 장비이다. 여러 PC를 쓰는 목적은 동시 작업이 아니라 CPU·iGPU·GPU 구성의 다양성 확보(성능·호환성 검증 폭 확대)이다. 따라서 장비는 이후 추가될 수 있으며, 새 PC 등록이 코드 구조 변경을 요구하지 않아야 한다. 각 문서의 확인 결과를 현재 설치 상태와 목표 설계 권장사항으로 나눠 기록한다. 아래 런타임·GPU 조합은 실제 전사 성능을 측정한 결과가 아니라 검증할 후보이다.

### 조합별 구현 권고

- **Samsung CPU:** 우선 CPU 실행 파일로 정확도·메모리·초 단위 처리율을 측정한다. 현재 Python 3.14.7/ORT 1.30.0은 사용자의 전역 환경 상태이므로 플러그인 런타임의 필수조건으로 삼지 않는다.
- **Samsung Intel iGPU:** 2026-11-02 CIM 조회에서 Intel Iris Xe(`VEN_8086&DEV_A7A0`)를 확인했다. 장치가 식별된 사실만으로 실행 provider가 준비된 것은 아니므로, 검증된 OpenVINO 기반 Windows 배포물의 드라이버·모델 호환성과 실제 iGPU 점유를 확인한다. 가속 실패 또는 이득 부족 시 CPU 선택은 계속 사용할 수 있어야 한다.
- **Lenovo CPU:** i7-10750H와 16 GB 환경에서 CPU 기준선을 만든다. 양자화 다국어 `small`부터 비교하고, 메모리나 처리시간이 부족하면 `base`로 낮추도록 모델 선택을 제공한다.
- **Lenovo Intel UHD Graphics:** 내장 GPU를 감지하고 검증된 Intel GPU provider가 이를 지원하는지 시험한다. Iris Xe와 UHD Graphics는 서로 다른 장치로 검사하며, 공통 provider 지원 및 실제 가속 여부를 별도로 확인한다.
- **Lenovo NVIDIA GPU:** 4 GB VRAM의 GeForce GTX 1650 Ti에서 작은 Whisper 모델과 GPU 분할/정밀도 설정을 우선 시험한다. GTX 계열은 모델·compute capability·CUDA 런타임 조합별로 호환성을 확인하고 provider가 실제 GPU에서 실행되는지 검증한다. 드라이버 버전만으로 CUDA/cuDNN ABI 호환성을 단정하지 않으며, 별도의 CUDA 툴체인 설치를 사용자 기본 전제로 두지 않는다.
- **두 장비 공통:** Windows x64용 CPU 실행 경로부터 안정화하고, 그 다음 검증된 GTX용 CUDA 및 Iris Xe/UHD용 Intel provider를 추가한다. 이번 계획은 Windows 데스크톱만 지원하며 macOS/Linux 구현·시험·배포를 포함하지 않는다. CPU 아키텍처를 provider manifest에서 분리해 향후 추가 아키텍처용 런타임을 연결할 수 있게 한다.

기본 모델 크기와 속도는 문서상 사양만으로 확정하지 않는다. 고정된 한국어 회의 샘플을 사용해 각 조합의 처리율(오디오 1분당 처리 초), 최대 메모리, 전사 오류, 발열·안정성을 측정하고 권장값을 정한다.

## 5. 설계 원칙

1. **CPU fallback 보장:** 호환되는 CPU 런타임이 설치되어 있으면 GPU provider 실패가 전체 전사 기능을 막지 않는다.
2. **실행 능력은 탐지와 검증으로 판단:** OS·아키텍처, 드라이버, 사용 가능한 런타임 provider, 모델 호환성을 확인하고 짧은 시험 추론까지 성공한 경우에만 가속기를 사용한다.
3. **엔진과 하드웨어 분리:** 전사 기능은 provider의 구체 구현이 아니라 정규화된 요청·결과 계약을 사용한다.
4. **vault와 설치물 분리:** 설정은 Obsidian 플러그인 데이터에 저장하되, 모델·실행 파일·캐시는 OS 사용자별 데이터 디렉터리에 둔다. 이를 통해 vault sync로 대형 바이너리나 다른 OS용 실행 파일이 복제되는 문제를 막는다.
5. **명시적 사용자 동의:** 내려받기 전 파일 출처, 크기, 라이선스, 버전을 표시한다. 설치와 실행은 사용자 설정 및 명시적 명령에 따른다.
6. **원본 보존 및 결과 검토:** 입력 오디오를 변경하거나 노트를 확인 없이 덮어쓰지 않는다.
7. **정확한 실패 표시:** 런타임·모델 경로 및 파일 검증·권한·드라이버·전사 오류를 구분해 알리고, 조용히 다른 엔진의 성공 결과처럼 보이게 하지 않는다.

### 두 PC 동시 개발 및 코드 확장성

이 절의 "개발 환경 전제"와 "PC 전환 절차"는 **개발자 개인의 작업 방식**이다. OneDrive, 순차 작업, PlugVaults 테스트 볼트는 개발자 환경을 적은 것이며 플러그인 사용자에게 요구하는 환경이 아니다. 플러그인은 사용자가 vault를 어떤 방식으로 동기화하는지(서비스 종류, 동기화 여부, 범위)를 가정하지 않는다. 제품 동작에 관한 요구는 "저장소·동기화 대상 구분"과 "코드 확장성"에 적고, 개발 환경 사례는 시험 시나리오의 하나로 취급한다.

#### 개발 환경 전제 (개발자 개인 방식)

- **작업 폴더:** 개발 소스는 OneDrive의 `%USERPROFILE%\OneDrive\OntheRecord`에 두고 여러 PC에서 동기화한다. 이후 Git 저장소로 연결하더라도 이 구조(OneDrive 동기화 작업 폴더)를 유지한다. 즉 Git은 이력·백업·원격 기준본을 담당하고, OneDrive는 PC 간 작업 폴더 동기화를 담당한다.
- **순차 작업:** PC들은 물리적으로 분리되어 있고 원격 작업을 하지 않으므로 같은 코드를 동시에 편집하는 일은 없다. 따라서 브랜치 병합 충돌 방지를 위한 복잡한 협업 절차는 요구하지 않고, **한 번에 한 PC만 작업한다**는 전제 위에서 PC를 바꿀 때의 인수인계 절차만 규정한다.
- **선례 워크플로(AssistantEmily):** 동일한 방식으로 개발 중인 `%USERPROFILE%\OneDrive\AssistantEmily` 플러그인과 같은 흐름을 따른다. 소스는 개발 폴더에서 관리하고, 빌드된 플러그인(`main.js`, `manifest.json`, `styles.css`)은 `%USERPROFILE%\OneDrive\PlugVaults`의 사용자 테스트용 Obsidian 볼트 `.obsidian\plugins\<플러그인 id>\`에 배포해 시험한다. 업무용 볼트는 시험에 사용하지 않고 PlugVaults로 볼트를 전환해 테스트한다.

#### PC 전환(인수인계) 절차

1. 작업을 마친 PC에서 변경을 커밋하고(Git 연결 후 원격으로 push) 빌드·배포 상태를 정리한다.
2. OneDrive 동기화가 완료됐는지(대기·오류 없음) 확인한 뒤 다른 PC에서 작업을 시작한다. 다른 PC에서 시작할 때도 동기화 완료와 `git status`로 작업 트리 상태를 먼저 확인한다.
3. Obsidian은 플러그인 파일을 연 채 동기화되는 상황을 피하기 위해 PC를 바꾸기 전 종료하거나 PlugVaults 볼트를 닫는다.
4. Git 계정이 1개이고 동시 편집이 없으므로 파일 내용의 병합 충돌은 발생 조건이 없다(기존 AssistantEmily에서도 충돌 사례 없음). 남는 위험은 동기화가 끝나기 전에 다른 PC에서 작업을 시작해 `.git`(`index`·`refs`·`objects`)이 일시적으로 불완전해지는 경우와 Git 쓰기 직후 PC를 전환하는 경우이며, 발생 가능성은 낮다. 전환 시 push와 동기화 완료 확인으로 충분히 완화하고, 이상이 생기면 `-PC이름` 복사본 파일을 정리하고 원격 저장소를 기준으로 복구한다.

#### 저장소·동기화 대상 구분

- 저장소(및 OneDrive 동기화)에는 소스, 의존성 lockfile, provider manifest 스키마, 테스트 샘플의 출처·해시와 개발 문서를 둔다.
- 런타임·모델 설치물, 캐시, 비밀 값, 기기별 절대 경로는 저장소·작업 폴더 동기화 대상에 넣지 않고 각 PC의 로컬 사용자 데이터 디렉터리에만 둔다(개발자 환경에서는 OneDrive로 대형 바이너리나 PC별 실행 파일이 다른 PC에 복제되는 것을 막는다). 제품 동작으로도 같은 위치 규칙을 적용해, 사용자가 어떤 방식으로 vault를 동기화·백업하든 설치물이 vault에 포함되지 않게 한다.
- `node_modules`와 같은 의존성 설치 폴더·빌드 산출물은 동기화 부담과 PC별 네이티브 의존성 차이를 만들 수 있다. 0단계에서 이들을 동기화 대상에서 제외하거나(예: 로컬 위치로의 링크 사용, 동기화 제외 설정) 각 PC에서 lockfile로 재생성하는 방식을 정해 `.gitignore`와 함께 문서화한다.
- **플러그인 설정의 분리(제품 설계):** 플러그인 `data.json`은 vault에 속하므로 vault를 복사·이동·동기화하면 다른 PC나 환경으로 전달될 수 있고, 사용자의 동기화 방식은 플러그인이 알 수 없다. 따라서 vault에 두어도 되는 설정(언어, 기본 모델 크기, 자동 감지 정책, 검색어·프로필, 삽입 위치)과 PC별 설정(선택한 실행 장치/provider, 사용자가 지정한 런타임·모델 경로 및 검증 상태, 장치 검증 결과)을 구분한다. PC별 값은 로컬 사용자 데이터 디렉터리에 저장하고, vault 설정의 장치 선호가 현재 PC에서 사용 불가하면 CPU로 안전하게 대체하되 사용자에게 알린다. 상세는 [SETTINGS_DESIGN.md](./SETTINGS_DESIGN.md)를 따른다.

#### 코드 확장성

- 설정 스키마와 provider 계약을 공통 기준으로 삼고 모든 PC에서 CPU 경로를 검증한다. GPU 시험은 각 PC의 실제 장치에서 수행하고 결과를 동일한 형식으로 기록한다(기기 식별자, CPU/iGPU/GPU 모델, 드라이버, provider·모델 버전, 처리율·메모리). 이 기록 형식(하드웨어 프로필 레코드)은 PC가 늘어나도 항목만 추가하면 되도록 한다.
- 하드웨어 감지, 런타임 검증, 전사 엔진, 모델 선택, 노트 출력을 분리해 PC별로 독립된 모듈을 개발·검증할 수 있게 한다. 한 PC의 GPU 전용 가정이나 로컬 런타임 상태가 다른 PC의 빌드를 막지 않아야 한다.
- 장비 목록을 코드에 하드코딩하지 않는다. 지원 판단은 장치 이름이 아니라 탐지·시험 추론 결과와 manifest로 하고, 새 CPU/iGPU/GPU 구성을 가진 PC가 추가되면 manifest·검증 기록 추가만으로 지원 범위를 넓힐 수 있게 한다.

## 6. 제안 아키텍처

```text
Obsidian Settings / File Picker / Review UI
                 |
      Recording Watcher + File Picker
                 |
       Auto-trigger Coordinator
                 |
       Transcription Service
       /          |           \
 Audio Normalizer  Runtime Validator  Result Formatter
       |                |
       +-------- Provider Registry
                 |-- whisper.cpp CPU
                 |-- NVIDIA GTX: CUDA (검증된 배포물만)
                 |-- Intel Iris Xe / UHD: OpenVINO (검증된 배포물만)
                 |-- 추가 Windows provider (후속 평가)
                 |
       Transcript Search (segment-level timestamps)
                 |
       향후 선택 분석 프로바이더
       |-- Word alignment / precise word timestamps
       |-- Proper-name candidate extraction
       |-- Speaker diarization
       |-- Acoustic scene / sound-event analysis
                 |
       User-managed Runtime + Model Store (vault 외부)
```

### 모듈 책임

- **Obsidian UI/Settings:** 플러그인 설정 탭에서 지속 설정을 관리한다. 파일 찾기 버튼, 전사 진행·취소, 결과 검토 UI는 작업 흐름에 제공한다.
- **Recording Watcher:** 공개 vault·노트 API의 변경을 관찰해 새/변경 오디오 파일과 활성 노트 링크를 추적한다. 코어 recorder 시작/종료 private 이벤트가 있다고 가정하지 않는다.
- **File Picker / Recording Resolver:** 파일 찾기 버튼으로 선택한 파일 또는 활성 노트의 오디오 링크를 해석하고, 지원 형식·파일 크기·읽기 가능 여부를 확인한다. 모호한 다중 파일은 사용자 선택을 받는다.
- **Auto-trigger Coordinator:** recorder 산출물의 생성·변경을 추적하고 파일이 안정화된 뒤 중복 없이 전사 대기열에 넣는다. 파일 선택 흐름은 선택 완료 즉시 대기열에 넣는다. 파일 쓰기 완료를 확신할 수 없으면 자동 실행을 보류하고 사용자에게 알린다.
- **Audio Normalizer:** 지원 포맷을 정규화된 오디오로 변환한다. 사용 가능한 디코더가 없으면 설치 상태와 지원 형식을 설명한다. 원본 파일은 읽기 전용으로 취급한다.
- **Transcription Service:** 작업 생성·취소·상태 이벤트, 중복 요청 방지, 처리 단계 간 오류 전파를 관리한다.
- **Transcript Search:** 전사문에서 사용자 지정 검색어를 찾고, 일치 텍스트가 포함된 전사 segment의 timestamp를 반환한다. 첫 단계에서는 이 timestamp를 단어 단위 위치로 표현하지 않는다.
- **Optional Analysis Adapters:** word alignment, 고유명사 후보 추출, 화자 분리, 환경음 분석은 각 기능이 별도 모델/provider를 필요로 할 수 있는 확장 지점이다. 기술·라이선스·품질·메모리·성능을 개별 검증하기 전에는 제품 기능으로 노출하지 않는다.
- **Provider Registry:** 설치·검증 상태, OS/아키텍처, 입력 형식, 모델, 실행 장치 및 메모리 제한을 기준으로 provider를 조회한다.
- **Provider Adapter:** 런타임 호출과 엔진별 출력을 공통 결과 형식으로 변환한다. 첫 adapter는 `whisper.cpp` CPU이며 가속 adapter는 개별 검증 후 등록한다.
- **Runtime Validator:** 사용자가 별도로 설치한 런타임·모델 경로를 확인하고 버전·해시·플랫폼 호환성·시험 실행을 검증한다. 플러그인 자체의 다운로드·설치·업데이트·삭제는 제공하지 않는다.
- **Result Formatter:** 전사 구간·타임스탬프·언어·엔진 정보를 Markdown으로 표현하고 삽입 위치를 처리한다.

### provider 공통 계약(설계)

각 provider는 다음 정보를 보고한다.

- 식별자와 버전, 라이선스, 지원 OS·CPU 아키텍처
- 지원 입력 포맷과 모델 ID/양자화, 언어, 실행 장치
- 필요한 드라이버·공유 라이브러리·외부 의존성
- 설치됨/검증됨 상태 및 실행 가능 사유
- `transcribe(input, model, options)`에 준하는 요청과 정규화된 결과
- 진행 이벤트, 표준 오류 진단, 취소 완료 여부

TypeScript 계약은 `src/provider.ts`에 둔다. provider 호출은 vault 내 오디오 경로·크기·확장자, 사용자 관리 모델 경로, 언어·장치 선호를 받으며 `AbortSignal`과 진행 콜백을 통해 취소 및 상태를 전달한다. 결과 timestamp는 초 단위 segment로 정규화한다. 알려진 실패는 provider 식별자와 공통 오류 코드로 표현하며 취소는 성공 결과로 반환하지 않는다. 이 계약 정의만으로 실제 provider의 설치·준비 상태 검증, 선택, 실행 또는 별도 worker가 구현된 것으로 간주하지 않는다.

첫 단계의 정규화 결과에는 언어, 전체 텍스트, 오디오 상대 시각 기준의 전사 segment 시작·종료 시각과 텍스트, 엔진·모델·실행 장치, 경고를 포함한다. whisper.cpp가 반환하는 timestamp의 실제 단위와 정밀도는 선택한 버전의 출력 계약과 시험 결과에 맞춰 기록한다. 전사문 검색 결과는 일치 문구와 해당 segment의 시간 범위를 연결한다. 이는 개별 단어의 시작·끝 시각을 보장하지 않는다.

향후 선택 분석 결과를 추가할 때에는 전사 원문과 별도 레코드로 보존하고, 사용된 모델/provider·버전·시간 단위·신뢰도 및 검증 상태를 함께 기록한다. 단어 정렬이 검증된 경우에만 word-level offsets를 제공한다. 고유명사, 화자, 음향 장면 추정은 각 별도 분석 기능의 결과이며 whisper.cpp CPU 전사 출력으로 가장하지 않는다.

지원/검증되지 않은 선택 기능은 사용할 수 없다고 명시한다. 텍스트 검색 결과, 단어 정렬, 음향 기반 화자 구분, 환경음 분류의 근거 출처를 서로 혼동하지 않는다.

가능하면 엔진은 Obsidian 프로세스 안에서 네이티브 모듈로 로드하지 않고 별도 프로세스로 실행한다. 이는 CPU 아키텍처별 ABI 충돌 및 엔진 장애가 Obsidian 전체에 미치는 영향을 줄인다. 프로세스 호출은 셸 문자열 조합이 아닌 인자 배열을 사용하고, 입력 경로는 검증된 vault 파일로 제한한다. 표준 출력은 구조화 결과, 표준 오류는 진단·진행 이벤트로 구분한다.

## 7. 사용자 관리 런타임 연결 화면

지속 설정은 환경설정의 **음성 전사 / 런타임** 섹션에서 관리한다. 런타임과 모델은 사용자가 공식 출처 등에서 별도로 취득·설치한다. 플러그인은 파일을 내려받거나 설치·갱신·삭제하지 않고, 경로 지정과 검증만 지원한다. 일회성 파일 선택·전사 진행·결과 검토는 명령/작업 UI에 둔다.

- 감지된 Windows 버전, CPU 아키텍처, 사용 가능한 메모리 및 지원 대상 가속 장치
- 사용자가 지정한 런타임·모델의 이름, 버전, 경로 상태, SHA-256 및 검증 결과
- 런타임·모델 경로 선택 및 사용자가 직접 설치·갱신하는 방법에 대한 문서 링크. 플러그인은 설치 파일·압축 파일을 가져오거나 이동하지 않는다.
- 언어·실행 장치(Auto/CPU/사용자가 설치한 가속 provider) 설정
- 자동 처리 설정: 코어 recorder 산출물 감지 사용 여부(초기 기본값 켬), 감지할 노트 범위, 파일 안정화 대기 조건, 자동 전사 사용 여부, 동시/중복 작업 정책 및 런타임 미설치 시 동작. 런타임이 준비되지 않은 경우 전사를 시작하지 않고 수동 설치 안내를 표시한다.
- 검색어·전사 프로필·기본 전사 모델 등 회의 때마다 반복 입력하지 않을 옵션
- 전사 완료 후 결과 검토를 요구하는 기본 정책 및 결과 삽입 위치/헤딩 설정. 전사 시작 자동화와 노트 수정 승인은 분리하며, 승인 전에는 노트를 변경하지 않는다.
- 기본 모델 선택 슬라이더: 사용자가 선택한 모델 크기를 기본값으로 저장해 다음 전사 작업에 적용한다. 지원되는 모델 크기를 순서대로 제공하고, 단계마다 모델명·파일 크기·권장 장치·예상 메모리·품질/속도 특성을 표시한다. 기기/provider에서 검증되지 않은 모델은 선택 불가 또는 경고 상태로 나타낸다. 파일 취득·설치는 플러그인 외부에서 사용자가 직접 한다.
- 전사문 검색 설정: 사용자 지정 검색어를 저장하고, 검색어가 발견된 전사 segment와 그 segment timestamp를 표시한다.
- 향후 분석 기능은 사용자가 별도로 설치한 모델/provider의 호환성·시험 추론이 확인된 경우에만 설정에 노출한다. 단어 정렬, 고유명사 추출, 화자 분리, 환경음 분석은 각각 별도 기능 상태로 관리하며, 미검증 기능을 사용 가능한 것처럼 표시하지 않는다.
- 현재 경로의 런타임·모델을 재검증하고, 라이선스·출처·파일 크기·필요 저장 공간과 공식 취득 안내를 표시한다.
- 사용자가 런타임·모델을 바꾼 뒤 수동으로 다시 확인할 수 있도록 검증 실행, 오류 진단, 경로 해제 기능을 제공한다. 파일 삭제·정리는 사용자가 직접 한다.
- 이미 설치된 로컬 런타임을 네트워크 연결 없이 사용할 수 있는 오프라인 동작

### 런타임 연결 및 무결성 확인

1. 플러그인은 앱 OS/아키텍처와 요구사항을 표시하고, 지원되는 런타임·모델의 공식 출처와 설치 방법을 안내한다. 네트워크 다운로드는 사용자가 플러그인 외부에서 수행한다.
2. 사용자는 본인이 취득·설치한 파일의 경로를 지정한다. 플러그인은 경로와 실행 파일을 허용된 사용자 로컬 데이터 디렉터리로 제한하고 vault 외부 접근 이유를 README에 설명한다.
3. 플러그인은 이미 있는 파일의 버전·파일 크기·SHA-256을 확인한다. 허용된 정확한 파일과 일치하지 않으면 실행하지 않고, 경로를 다시 지정하도록 안내한다. 플러그인은 파일을 이동·압축 해제·교체·삭제하지 않는다.
4. 로컬 시험 추론으로 provider를 확인하고 성공한 조합만 사용 가능으로 표시한다. 실패해도 기존 파일을 변경하거나 정리하지 않는다.
5. 업데이트와 제거는 사용자가 해당 배포처 및 운영체제의 절차에 따라 플러그인 외부에서 직접 수행한다. 그 뒤 설정에서 다시 검증한다.

## 8. 전사 및 노트 반영 설계

### 전사 작업의 자동 트리거

- 플러그인 설정 화면에서 자동 녹음 감지와 자동 전사 여부를 설정한다. 설정값은 vault의 플러그인 설정으로 저장하고, 회의 중 매번 같은 옵션을 입력하게 하지 않는다.
- 코어 Audio recorder의 녹음 시작/종료 동작 자체를 공개 API가 이벤트로 제공한다고 전제하지 않는다. 공개 vault/metadata 이벤트로 새 파일·노트 링크를 감지할 수 있는지 먼저 확인한다. 파일 생성/수정 중에는 녹음 중 후보로 추적하고, 수정 시각/크기가 설정된 안정화 기간 동안 변하지 않고 노트 링크도 확인되면 녹음 완료로 간주해 자동 전사를 시작한다.
- 공개 API만으로 시작 상태를 안정적으로 구분할 수 없더라도 코어 플러그인 내부 구현이나 private event를 우회 사용하지 않는다. 종료 후 링크/파일 발견 및 안정화 감지를 우선하고, 감지가 불가능하면 상태를 알린 뒤 파일 찾기 버튼으로 복구하게 한다.
- 사용자가 플러그인의 **파일 찾기** 버튼을 클릭해 vault 오디오 파일을 선택하면, 별도 전사 명령이나 추가 확인 없이 선택 파일을 자동으로 대기열에 넣는다. 파일이 미지원·손상·쓰기 중이면 원인을 표시하고 전사를 시작하지 않는다.
- 자동 트리거는 전사 작업 시작을 자동화할 뿐 결과 삽입까지 자동 승인하지 않는다. 완료 후 결과를 미리보기하고 사용자가 승인해야 노트를 변경한다.
- 같은 파일에 대해 반복 이벤트가 발생해도 파일 경로와 수정 시각/크기 등 작업 식별 기준으로 중복 대기열·중복 전사를 방지한다. 재전사는 사용자가 별도로 요청하고 기존 결과 추가/교체를 확인한다.

### 입력과 오디오 처리

- 기본 입력: 활성 회의 노트의 첨부 링크 중 오디오 파일.
- 대체 입력: 플러그인의 파일 찾기 버튼에서 사용자가 고른 파일. 선택 즉시 자동 전사 대기열에 들어간다.
- 외부 경로 입력은 초기 버전에서 명시적으로 허용 여부를 결정하고, 허용 시 vault 파일과 동일하게 경로·권한을 검증한다.
- 오디오 입력은 스마트폰 및 범용 미디어에서 널리 사용되는 `.m4a`, `.mp3`, `.wav`, `.aac`, `.ogg` 확장자를 지원한다. 코어 Audio recorder 녹음(`.m4a`)과 스마트폰에서 가져온 파일을 모두 입력할 수 있어야 한다.
- 확장자만으로 코덱이나 실제 파일 형식을 단정하지 않는다. 파일 시그니처/컨테이너를 검사하고, 각 형식의 주요 오디오 코덱을 검증된 디코더로 임시 PCM/WAV에 정규화한다. 잘못된 확장자, 손상 파일, 미지원 코덱은 원인을 표시하고 거절한다.
- 변환기와 decoder는 provider 계약 뒤에 두어 포맷 추가를 전사 엔진 변경과 분리한다. 변환은 원본을 변경하지 않으며 임시 파일은 작업 종료 후 정리한다.
- 임시 음성 데이터는 전사 완료·취소·실패 후 정리한다. 원본은 그대로 둔다.
- 길이·크기 상한, 여유 디스크, 오디오 읽기 권한을 시작 전에 확인한다.

### 첫 단계에서 제공할 전사 및 검색

- `whisper.cpp` CPU 실행으로 오디오의 발화 텍스트와 엔진이 제공하는 segment timestamp를 출력한다.
- 사용자가 지정한 단어·문구는 전사된 텍스트에서 검색한다. 일치한 문구가 포함된 segment의 시작·끝 시각으로 원본 녹음을 재생할 수 있게 한다.
- 이 검색은 전사 텍스트 기반이다. 음성 인식에서 누락된 말, 동음이의어, 표기 변형을 모두 찾아준다고 보장하지 않으며, 일치 timestamp도 단어 내부 위치가 아니라 해당 segment 범위다.
- 이름·지역명·회사명·제품명도 먼저 전사된 단어/문구로 검색할 수 있지만, 자동 개체명 인식 또는 분류 기능으로 표현하지 않는다.

### 결과 미리보기와 기록

- 전사 및 지원되는 검색 결과를 미리보기·편집할 수 있고 사용자가 취소하면 노트를 수정하지 않는다.
- 삽입 방식: 커서 위치, 활성 노트의 지정 헤딩 아래, 새 전사 노트 중 설정 가능한 방식.
- 기본값은 명시적 헤딩 아래 삽입하며, 동일 녹음의 반복 전사 시 기존 결과를 덮어쓰지 않고 추가/교체 여부를 묻는다.
- 타임스탬프 포함 여부, 줄바꿈, 언어, 사용 모델, 검색 결과 삽입 여부는 템플릿으로 관리한다.
- 첫 단계 회의록 기능은 `전사 원문 및 segment timestamp → 사용자의 전사문 검색/검토 → 선택한 결과 반영`으로 구성한다. 전사 내용에 없는 결정·참석자·할 일을 만들어내지 않는다.
- timestamp는 검증된 엔진 출력의 오디오 상대 segment offset으로 저장한다. 단어 수준 aligner가 별도로 검증·설치되지 않으면 단어 내부 시각을 제공하지 않는다.

## 9. 상황특화 프로필 확장

상황특화는 녹음 원본과 연결된 시간 기반 분석을 포함하는 장기 제품 방향이다. 구현은 기능별로 분리하고 각 모델/provider의 실제 능력과 검증 상태에 따라 활성화한다.

- **첫 구현(whisper.cpp CPU):** 음성 전사, 엔진이 출력하는 segment timestamp, 전사문에서 사용자가 입력한 검색어를 찾고 일치 segment로 이동하는 기능.
- **추가 검증 후 가능한 기능:** 더 정밀한 단어 수준 timestamp는 별도 forced-alignment/word-alignment 도구와 모델이 필요할 수 있다. 고유명사 후보 분류는 별도 NLP/NER 처리와 한국어 품질 검증이 필요하다. 검증 전까지 검색어/후보 시각은 전사 segment 단위로만 연결한다.
- **별도 연구·확장 기능:** 화자 분리에는 별도 diarization 모델/provider가 필요할 수 있으며, `whisper.cpp` 자체가 수행한다고 가정하지 않는다. 음향 장면/환경음 분류 또한 전사 모델의 기능으로 보지 않고 별도 audio-classification 모델이 필요하다고 본다. 특정 장소·상황의 사실 판정은 기능 목표로 삼지 않는다.
- 프로필 예: 일반 회의, 인터뷰, 상담, 강의/세미나 등. 실제 지원은 해당 프로필의 용어·검색어와 검증된 기능 조합에 한정한다.
- 프로필 설정: 기본 언어, 관심 검색어, 출력 헤딩·템플릿, 검증된 provider가 지원하는 경우에만 적용되는 추가 기능.
- 미설치·미지원·미검증 기능은 UI에서 상태와 한계를 표시하고, 실행 또는 결과가 있는 것처럼 가장하지 않는다.
- 사용자가 검색어를 직접 입력하면 전사문에서 확인되는 일치만 제공한다. 음성 인식이 말을 누락했거나 표현이 달라진 경우도 있으므로 미검출은 실제 발언이 없었다는 뜻이 아니다.
- 원문 전사와 요약/액션아이템은 각각 켜고 끌 수 있게 하고, 후처리 결과는 원문과 구분하여 보존한다.
- 사용자의 vault 노트 내용을 외부로 보내는 기능은 기본 제공하지 않는다. 향후 클라우드 모델을 추가한다면 별도 opt-in, 전송 데이터 미리보기, 보존 정책 안내가 필요하다.

## 10. 호환성과 지원 정책

### 플랫폼·아키텍처 모델

플랫폼 키를 `OS + CPU 아키텍처 + provider + 필요 드라이버/런타임`의 조합으로 정의한다. 이번 릴리스의 catalog는 Windows 데스크톱만 포함하며, 예시는 `windows-x64-cpu`, `windows-x64-cuda`, `windows-x64-openvino`이다. 실제 배포는 빌드·라이선스·시험이 완료된 조합만 등록한다. CPU 아키텍처 분기는 provider 구현에서 분리해 향후 Windows의 추가 아키텍처를 연결할 수 있게 한다.

- **기본 호환성:** 이번 지원 기준은 두 PC와 같은 Windows x64에서 동작하는 CPU provider이다.
- **선택 호환성:** NVIDIA GTX CUDA와 Intel Iris Xe/UHD Graphics 가속은 각 GPU·드라이버·런타임·모델 조합을 시험해 capability로 표시한다. iGPU와 dGPU를 구별하며, GPU 실행 검증 전에는 가속 가능으로 표기하지 않는다.
- **우선 지원 검증 대상:** Samsung/Lenovo 두 PC의 Windows x64 CPU, GTX 1650 Ti, Intel Iris Xe 및 Intel UHD Graphics. 이 계획에서 macOS/Linux용 artifact, 구현, CI, 지원 시험은 제외한다.
- **미지원 조합:** 자동으로 CPU 경로를 제안하거나, CPU 바이너리도 없으면 이유와 지원 요청 경로를 안내한다.
- **Desktop Only:** 지원 대상은 Obsidian 데스크톱 앱이다. Obsidian 모바일 앱에서는 플러그인 실행·전사를 지원하지 않으며, 모바일 호환성을 릴리스 요건으로 삼지 않는다.
- **의존성 정책:** 시스템에 설치된 Python·Node 패키지·ONNX Runtime을 묵시적으로 재사용하지 않는다. 필요하다면 지원 버전을 명시하고 설정 화면에서 검사한다.
- **다중 PC 개발:** 모든 PC가 같은 의존성 lockfile·manifest 형식·테스트 절차를 사용하며, 작업은 PC를 바꿔가며 순차적으로 진행한다(동시 편집 없음). 공통 CPU 시험은 모든 PC에서, 각 GPU provider 시험은 해당 GPU가 있는 PC에서 수행한다. 상세 절차는 5절 "두 PC 동시 개발 및 코드 확장성"을 따른다.

## 13. 검증 및 승인 기준

### 기능 기준

- 코어 Audio recorder가 현재 노트에 삽입한 링크와 여러 오디오 링크에서 올바른 입력을 선택한다.
- 코어 녹음 산출물의 생성·변경을 공개 API로 감지하고, 녹음 중에는 전사하지 않으며 저장 완료 후 안정화 조건을 충족했을 때 전사를 자동 시작한다. 이 동작은 자동 연동 요구사항이므로 감지가 불가능하면 구현 범위의 blocker로 기록하고, 자동 지원이 된다고 표시하지 않는다. 파일 찾기 버튼은 별도의 대체 입력 경로로 유지한다.
- 파일 찾기 버튼에서 지원 오디오 파일을 선택하면 별도 전사 명령 없이 즉시 자동 전사를 시작한다. 선택한 파일이 쓰기 중이거나 손상/미지원이면 전사를 시작하지 않고 이유를 알린다.
- 자동 감지 이벤트가 반복되어도 같은 오디오를 중복 대기열/중복 전사하지 않으며, 설정 화면에서 감지와 자동 전사를 끄거나 기본 동작을 조정할 수 있다.
- 모델·언어·장치·프로필·자동 감지 등 지속 옵션은 Obsidian 플러그인 설정 화면에서 저장·관리하며, 작업 UI에는 파일 선택·진행·취소·검토 같은 일회성 동작만 둔다.
- `.m4a`, `.mp3`, `.wav`, `.aac`, `.ogg` 파일을 각각 선택해 실제 컨테이너·코덱을 검사하고 지원되는 경우 공통 오디오 입력으로 변환한다. 손상 파일과 지원되지 않는 코덱은 원인을 표시하고 거절한다.
- 첫 구현의 timestamp는 검증한 `whisper.cpp` 출력의 segment 단위이다. 단어 내부 시작·끝 시각은 별도 정렬 모델/provider를 검증하기 전에는 요구하거나 표시하지 않는다.
- 사용자가 검색어를 지정하면 전사 결과에서 확인된 각 일치 문구와 포함 segment의 시각으로 이동할 수 있다. 전사문에 없는 검색어는 “전사문에서 찾지 못함”으로 표시하며 녹음에 실제로 없었다고 단정하지 않는다.
- 사람 이름·지역명·회사명·제품명은 사용자가 입력한 검색어로 찾을 수 있지만, 첫 구현에서 자동 개체명 인식·분류·완전 검출을 보장하지 않는다. 자동 추출은 별도 NLP/NER 기능으로 검증 후에만 추가한다.
- 첫 구현은 화자 분리와 환경음/공간 분석을 제공하지 않는다. 향후 별도 모델/provider가 추가되어 검증된 경우에도 실제 장소나 화자 신원을 자동 확정하지 않는다.
- 지원하지 않는 형식, 누락/손상 파일, 런타임·모델 경로 또는 검증 오류, 권한 거부, 디스크 부족을 구별해 알린다.
- 경로 검증·전사 실패 뒤 원본 녹음·기존 노트가 유지되며, 플러그인은 런타임·모델 파일을 변경하지 않는다.
- 동일 오디오를 다시 처리할 때 기존 텍스트를 묵시적으로 덮어쓰지 않는다.
- CPU provider만 설치한 환경에서 전사 기능이 완결된다.
- 모델 설정의 슬라이더에서 현재 장치/provider에 지원되는 모델 단계를 선택하고 저장할 수 있다. 선택 모델의 크기·필요 용량·권장 장치를 확인할 수 있으며, 지원되지 않는 조합은 사용할 수 없다.
- 미검증 상황 분석 모델/provider를 제품 설정에 노출하지 않는다. 향후 검증을 통과한 확장만 STT 모델과 독립된 capability로 표시한다.
- Windows x64 CPU 전사와 설치 기능은 모든 개발 PC에서 동일한 공통 코드·lockfile·테스트 절차로 재현할 수 있다.
- 개발자는 빌드 결과를 PlugVaults 테스트 볼트에 배포해 설치·설정·전사 흐름을 확인한다(개발자 개인 시험 환경). 업무용 볼트는 시험에 사용하지 않는다.
- `data.json`에 다른 환경에서 저장된 장치 선택이 들어 있어도 현재 PC에서 오류 없이 CPU 등 사용 가능한 경로로 대체되고, 런타임·모델 설치물은 vault에 저장되지 않는다. 시험 시나리오는 vault를 동기화하는 경우(개발자의 OneDrive 환경 포함)와 동기화하지 않고 단일 PC에서 쓰는 경우를 모두 포함한다.
- 자동 가속은 실제 시험 추론 성공 후에만 사용하고, GPU 오류·메모리 부족 시 사용자에게 상태를 알린 후 동의를 받은 CPU fallback을 수행한다.

### 품질 및 호환성 기준

- 동일 샘플과 언어 설정으로 두 기기의 CPU 결과를 비교한다. 가속 여부와 관계없이 텍스트·세그먼트 형식은 공통 계약을 만족해야 한다.
- segment timestamp 및 전사문 검색 결과를 라벨링된 오디오로 검증한다. 고유명사 자동 추출의 정밀도는 해당 확장 기능의 별도 검증 전까지 주장하지 않는다.
- word alignment, 화자 분리, 음향 장면 분석은 별도 기술 검증 단계에서 별도 정답 세트로 평가한다. 측정되지 않은 정확도·신뢰도·identity 결과를 UI에 단정적으로 제시하지 않는다.
- 성능 측정에는 오디오 길이 대비 처리시간, 최대 RAM/VRAM, 실패율, 샘플 전사 오류 지표를 기록한다. 이를 근거로 권장 모델과 최소 사양을 정한다.
- 사용자가 지정한 런타임 artifact는 OS·아키텍처·버전·해시 검증에 실패하면 실행되지 않는다.
- 플랫폼별 smoke test에서 런타임 탐지, 경로·파일 검증, 짧은 시험 추론, 경로 해제, CPU fallback을 검사한다. 플러그인이 파일을 설치·취소·제거하는 동작은 구현하지 않는다.
- Obsidian 플러그인 API와 사용 가능한 OS 프로세스 접근은 대상 Obsidian Windows 데스크톱 버전에서 검증한다. 릴리스 대상은 Windows Desktop Only이며, 모바일·macOS·Linux 호환성 시험이나 배포는 수행하지 않는다.

## 15. 선결 결정과 후속 검토 항목

아래 결정은 이번 범위에서 확정하며, 필요한 구현 검증은 0단계와 관련 개발 단계에서 수행한다.

1. **오디오 입력 포맷 및 변환기**
    - 코어 Audio recorder가 생성하는 `.m4a` 파일을 확인했다. 스마트폰에서 가져오는 오디오도 처리 대상으로 삼는다.
    - 1차 지원 확장자는 널리 사용되는 다섯 형식 `.m4a`, `.mp3`, `.wav`, `.aac`, `.ogg`로 정한다. 이는 구현 목표 형식 목록이며, 모든 스마트폰 앱의 모든 코덱 조합이 자동 지원된다는 뜻은 아니다.
    - 확장자 외에 파일 시그니처·컨테이너·코덱을 검사하고, 각 형식의 검증된 오디오 코덱을 임시 PCM/WAV로 변환해 provider에 전달한다. 손상 파일과 지원되지 않는 코덱은 원본을 변경하지 않고 상세 원인과 함께 거절한다.
    - 실제 테스트 샘플은 각 확장자별로 수집해 코덱, 채널, 샘플레이트, 변환 결과를 회귀 테스트한다. `.3gp`, `.amr`, `.flac` 등 추가 형식은 이번 다섯 형식의 안정화 후 별도 범위로 검토한다.
2. **두 PC의 동시 개발 방식 및 코드 확장성**
    - (개발자 개인 방식) 작업 폴더는 OneDrive의 `STT`로 유지하고(Git 저장소로 연결해도 동일), 원격 Git 저장소를 기준본·복구 수단으로 쓴다. PC는 물리적으로 분리되어 있고 원격 작업이 없으므로 동시 편집은 발생하지 않으며, PC 전환 시 커밋·push와 OneDrive 동기화 완료 확인 절차를 따른다. 공통 lockfile·provider manifest·테스트 절차를 유지한다.
    - 다중 PC 사용 목적은 CPU·iGPU·GPU 다양성 확보이며, 두 대를 넘어 PC가 추가되어도 하드웨어 프로필 기록과 manifest 추가만으로 확장한다.
    - (개발자 개인 방식) 개발·배포는 AssistantEmily와 같은 방식으로 한다. 소스는 `STT`에서 관리하고 빌드 결과는 `%USERPROFILE%\OneDrive\PlugVaults` 테스트 볼트에 배포해 시험한다.
    - 런타임과 모델은 각 PC의 로컬 관리 디렉터리에 설치하고 vault, Git, 작업 폴더 동기화로 실행 파일·모델·캐시를 복제하지 않는다(제품 동작). 플러그인 설정은 vault 설정과 PC별 설정으로 분리한다.
    - 공통 Windows x64 CPU 기능과 사용자 관리 런타임 연결·검증 흐름은 양쪽 PC에서 확인한다. Samsung은 Iris Xe, Lenovo는 UHD Graphics와 GTX 1650 Ti의 각 provider를 장치별로 검증한다.
    - 하드웨어 탐지, provider, 전처리/decoder, 모델 선택, 노트 출력 모듈의 경계를 고정하여 새 CPU 아키텍처와 provider를 기존 코어 흐름 변경 없이 추가할 수 있게 한다.
3. **GPU 지원 범위**
    - NVIDIA GeForce GTX 계열 및 Intel Iris Xe와 Intel UHD Graphics를 가속 후보로 다룬다. NVIDIA는 CUDA provider, Intel iGPU는 OpenVINO 등 검증된 Windows provider를 후보로 한다.
    - GTX 세대/compute capability, Intel GPU 세대, 그래픽 드라이버, provider/runtime 버전, 모델 크기별로 호환성을 확인한다. GPU가 감지되는 것만으로 가속을 지원한다고 표기하지 않고 시험 추론과 실제 GPU 실행을 확인한다.
    - GTX 1650 Ti의 4 GB VRAM과 두 장비의 16 GB 시스템 메모리를 기준으로 작은 모델부터 측정한다. provider나 메모리 조건이 충족되지 않으면 CPU 전사로 사용할 수 있어야 한다.
4. **전사 모델의 환경설정**
    - 사용자가 환경설정 화면의 모델 크기 슬라이더로 기본 전사 모델을 고르고 설정에 저장하도록 한다. 설치 시 고정 모델 하나만 강제하지 않는다.
    - 슬라이더는 provider·장치 조합에서 검증된 모델 단계만 제공하며, 모델명·파일 크기·필요 저장 공간·예상 메모리·권장 장치를 표시한다. 메모리/가속기 호환성이 없는 선택은 비활성화하거나 경고한다.
    - 초기 권장 단계는 두 PC에서 측정한 품질·속도·메모리를 바탕으로 정한다. 사용자가 더 크거나 작은 모델을 선택하면 필요한 파일을 명시적으로 설치한 뒤 전사에 적용한다.
5. **노트 출력 정책**
    - 활성 노트 삽입 위치, 타임스탬프 기본값, 재전사 시 추가/교체 동작은 원본 보존을 기본으로 설계하고 구현 전 UI 흐름에서 검토한다.
6. **이번 릴리스 플랫폼**
    - Obsidian Desktop Only, Windows x64를 1차 구현·시험·배포 대상으로 한다. Windows용 CPU 아키텍처별 runtime/provider 설계를 분리하되, 현재 확인된 두 PC 외 아키텍처의 출시 여부는 실제 artifact 검증 후 별도 결정한다.
    - 모바일, macOS, Linux의 설치·실행·전사·런타임 배포와 호환성 시험은 이번 개발계획에서 제외한다. 다른 데스크톱 OS 지원은 후속 개발계획으로 분리한다.
7. **상황특화 범위**
    - 제품의 장기 방향에는 회의 관련 단어/고유명사의 녹음 내 위치, 화자 분리, 주변 환경음·공간 단서가 포함될 수 있다. 이는 모든 기능이 이번 릴리스에 포함되거나 `whisper.cpp` CPU로 구현된다는 약속이 아니다.
    - 첫 구현은 검증된 `whisper.cpp` CPU 전사와 그 엔진이 실제 출력하는 segment timestamp, 전사문 내 사용자 검색어의 segment-level 위치 연결로 제한한다. 사람 이름·지역명·회사명·제품명은 사용자가 입력한 검색어로 찾을 수 있으나 자동 인식·분류 기능으로 표시하지 않는다.
    - 단어 수준 정렬과 자동 고유명사 후보 추출은 별도의 정렬/NLP 모델과 품질·라이선스 검증을 통과한 뒤에만 추가한다. 해당 기능의 timestamp 정밀도는 통합한 provider가 실제 제공하는 범위로 제한한다.
    - 화자 분리와 환경음·공간 분석은 `whisper.cpp`의 기능으로 취급하지 않는다. 각각 독립된 모델/provider가 필요할 수 있는 후속 연구 항목이며, Windows 두 PC에서 품질·리소스·실행 방식이 검증되기 전까지 제품 UI·필수 기준에 포함하지 않는다. 음향 추론만으로 화자 신원·실제 장소·상황을 확정하지 않는다.
    - 사용자 확인, 프로필 및 회의록 후처리는 위 기능의 실제 구현 범위에 맞춰 별도 설계한다. 구현되지 않은 능력을 계획서에서 완료 기능처럼 표현하지 않는다.
8. **GPU 성능 확장 조건**
    - 우선 CPU whisper.cpp 기준선을 만들고, 동일 오디오·모델·결과 형식으로 CPU와 GPU를 비교한다. GPU provider를 지원하는 이유는 측정된 처리시간·메모리 또는 필요한 모델 크기에서 이점이 있을 때로 한정한다.
    - GPU 추가는 `whisper.cpp` 전사 처리량을 개선할 수 있지만, 단독으로 word alignment, NER, 화자 분리 또는 음향 장면 이해 기능을 제공하지 않는다. 각 기능에 필요한 별도 알고리즘/model과 GPU 호환성은 독립적으로 검증한다.
    - 속도·메모리 개선이 유의미하지 않거나 드라이버/모델 호환성이 불안정하면 해당 provider를 배포하지 않고 CPU 경로를 유지한다. 수치상 성능 목표는 두 PC에서 기준 측정을 한 후 설정한다.
9. **설정 화면과 자동 전사 트리거**
    - 모델·언어·장치·프로필·자동 감지/전사·결과 삽입 위치 등 반복 사용하는 설정은 Obsidian 플러그인 설정 화면에서 관리한다. 회의 중에는 코어 Audio recorder 사용 또는 플러그인 파일 찾기를 통해 전사 작업이 자동 시작되어야 한다.
    - 녹음 시작 시 공개 API로 관찰 가능한 산출물 생성을 추적하고, 녹음 중에는 전사하지 않는다. 코어 recorder의 파일 생성 후 안정화를 기다리고, 공개 MetadataCache로 활성 노트의 오디오 링크가 확인된 뒤 자동 전사한다. 링크 확인이 제한 시간 내 되지 않으면 자동 처리를 중단하고 사용자가 알 수 있도록 안내한다. 파일 찾기 버튼에서 사용자가 파일을 고른 경우에도 선택 직후 자동 전사한다.
    - Obsidian 공개 API로 이 흐름을 구현할 수 있는지 0단계에서 검증한다. 내부/private event에 의존하지 않으며, 공개 API만으로 시작/종료를 안정적으로 구분할 수 없으면 이를 자동 지원한다고 주장하지 않고 설계 blocker와 제약을 기록해 해결책을 결정한다. 파일 찾기는 감지 실패 시의 대체 입력 경로다.
    - 자동 전사는 전사 작업 시작에만 적용하고, 노트 반영은 검토·사용자 승인 후 수행한다. 완료 후 결과를 자동 삽입하거나 기존 노트를 자동 덮어쓰는 요구는 이번 범위에 포함하지 않는다.
