# 0-OBS-02: 파일 안정화 감지 조건 시험

작성일: 2026-11-03 / 상태: **완료(코어 Audio recorder 실제 녹음 4건 확인)**

## 1. 배경

[OBS-01](./OBS-01_AUDIO_RECORDER_EVENT_PROBE_2026-11-02.md)에서 녹음 산출물의 `create` 이벤트는 관찰되었지만, 녹음 중 `modify` 이벤트는 관찰되지 않았다. 따라서 "쓰기가 끝났는지"는 이벤트가 아니라 **파일 상태(크기·수정 시각)를 주기적으로 확인**해 판정한다.

## 2. 판정 조건

구현: [stability.ts](../../src/stability.ts) `waitForStable`. Obsidian에 의존하지 않는 순수 함수로, 상태 조회·시계·대기 함수를 주입받는다.

| 항목 | 기본값 | 의미 |
|---|---:|---|
| `intervalMs` | 1,000 | 상태 확인 간격 |
| `quietMs` | 5,000 | (크기, 수정 시각)이 이 시간 동안 같으면 안정화 |
| `minSizeBytes` | 0 | 이 크기 이하(0 바이트 포함)는 안정화로 보지 않음 |
| `timeoutMs` | 4시간 | 이 시간까지 안정화되지 않으면 포기 |
| `maxMissingChecks` | 5 | 파일이 연속 사라지면 `missing`으로 종료 |

결과 상태: `stable`, `timeout`, `missing`, `cancelled`. 결과에는 대기 시간, 확인 횟수, 변경 횟수가 포함된다. 변경 횟수가 0이면 생성 시점에 이미 완성된 파일(복사·동기화 등)이다.

## 4. 한계와 위험

- **일시정지 구분 불가:** 녹음 중 일시정지로 `quietMs` 이상 파일이 변하지 않으면 안정화로 오판할 수 있다. 코어 Audio recorder는 종료 시 파일을 한 번에 만드는 것으로 확인되어(§5) 이 녹음기에서는 해당되지 않으나, 다른 녹음 앱은 미확인이다.
- **recorder의 쓰기 방식:** §5에서 확인(종료 시 한 번에 생성, 변경 0회).
- 동기화 폴더(OneDrive)에서 다른 PC가 파일을 내려받는 경우 단계적 기록이 `modify`로 보일 수 있다. 같은 로직이 적용된다.
- 안정화 이후 같은 파일이 다시 수정되는 경우(이어 녹음 등)는 아직 처리하지 않는다.

## 5. 실제 Audio recorder 시험 결과 (2026-11-03, 사용자 수행)

테스트 볼트 `PlugVaults`, Obsidian 1.14.4, 코어 Audio recorder로 4회 녹음(약 5~23초). 개발자 콘솔 로그:

| 파일 | 크기 | 대기 | 변경 횟수 |
|---|---:|---:|---:|
| 녹음 1 | 7 KB | 5초 | 0 |
| 녹음 2 | 4 KB | 5초 | 0 |
| 녹음 3 | 83 KB | 5초 | 0 |
| 녹음 4 | 205 KB | 5초 | 0 |

로그의 크기는 볼트 파일 크기(7,141 / 4,021 / 85,046 / 210,077 바이트)와 일치한다. 파일 수정 시각도 모두 생성 시각과 같은 초였다.

- **코어 recorder는 녹음 중에 파일을 키우지 않고, 종료 시 완성된 파일을 한 번에 생성한다**(변경 0회). 따라서 파일 생성 시점이 곧 녹음 종료 시점이고, 일시정지로 인한 조기 오판은 이 녹음기에서는 발생하지 않는다.
- 안정화 판정은 최소 대기(`quietMs`)만 거치고 즉시 통과했다.
- **`quietMs`는 5초로 확정한다.** 이번 녹음기만 보면 더 짧아도 되지만, 동기화·복사·외부 앱이 만든 오디오 파일은 단계적으로 써질 수 있어 5초를 유지한다.
- 한계: 4건, 코어 recorder 한 종류, 한 대의 PC. 일시정지 시험은 별도로 구분하지 않았다. 다른 녹음 앱·동기화로 들어오는 파일의 쓰기 방식은 미확인이다.
- 디버그 로그는 콘솔 `Verbose` 수준에서만 보인다. 알림은 설정과 무관하게 표시된다.
